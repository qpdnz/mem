# domain-map — 業務とデータの地図を1枚のHTMLにする

## この skill が作る物

`.doc/<名前>/` に2つ置く。

- `map.json` — **地図の正本。**実体・項目・関連・業務の流れ・画面を1つに書いた定義
- `index.html` — その定義から組み立てた1枚 (外部への通信なし。開けばそのまま動く)

**図はすべて同じ1つの定義から描く。**図ごとに別の絵を描かない。片方だけ直って片方が古い、が起きないこと自体がこの形式の値打ち。

| 図 | 見せる物 |
|---|---|
| 概念図 | 実体と関連。「何と何が、どういう言葉でつながっているか」 |
| ER図 | 同じ実体を表として。項目名・物理名・PK/FK/UQ・参照先 |
| 業務フロー | 誰が・何を・どの順で。各段階が読み書きする実体 |
| 画面UI | 画面の線画と遷移。画面ごとの「すること」と「使うデータ」 |
| 用語 | 図に出る語を引く頁。**1行の意味と「まぎらわしい点」。**初めて見る人はここから読む |

右の欄はどの図でも共通で、選んだ物の項目・つながり・出典を出す。下の帯で図の切替・検索・▶での筋書き再生・拡大縮小をする。

## 規律 (先に読む)

- **作れない根拠は「不明」と書く。それが最も価値のある結果。**もっともらしい説明で埋めない。推測は「推測:」と明示する。
- **実体ごとに `source` (出典) を付ける。**実際に開いて確かめた `file:行` だけを書く。開いていない物を出典にしない。
- **名前で判定しない。**型名・file名・role名は実体の証拠にならない。中身を読んで判定する。
- **数の主張は数えてから書く。**「〜だけ」「全部」と書くときは、その外側を1つ以上確かめる。
- 地図は**その時点の写し**。`meta.basis` に「どの commit と、いつまでの実測か」を必ず書く。

根拠: 実測 2026-09-16。auto_work 自身の地図を作ったとき、台帳の `completion_status` に code にも prompt にも定義の無い2語 (`image_required` / `verification_required`) が101件あった。「不明」と書ける形にしていなければ、実在する4語の仲間として並べてしまう。

## 手順

### 0. 対象と範囲を決める

$ARGUMENTS が対象。空なら直前の会話で頼まれた物を対象にする。それも無ければ聞く。

最初に**1文で書く**: 「この地図は、誰が何を分かるための物か」。
そこから外れる実体は入れない。20前後の実体で足りないなら、たいてい範囲が広すぎる。

`--update .doc/<名前>` が付いていたら [更新するとき](#更新するとき) へ。

### 1. 実物から材料を集める

読む物は対象で変わる。典型は次の6つ。**docではなく実物を読む。**

| 材料 | どこから |
|---|---|
| 実体と項目 | DBのDDL・schema、型定義 (`Vo_` 等)、frontmatter を解析している code |
| 値の範囲 | enum の宣言 (メンバー名と数値)、実データの `SELECT DISTINCT` |
| 関連 | FK・参照解決している code・実データのid一致 |
| 業務の流れ | 状態遷移を実行している method、指示文 (prompt)、実行記録 |
| 画面 | 画面を組み立てている code の文字列 literal、layout、押した時に呼ばれる処理 |
| 実測 | 記録DB・log。件数・最初と最後の時刻・観測されている値 |

読む量が多いなら**読み取り専用の subagent へ分けてよい** (この repository では [委任の境界](../../../.rule/self/maintenance.md#委任の境界-subagent--workflow) に従う)。その時は指示へ次を必ず入れる。

- 生の実測値 (件数・時刻・path・原文) を返す。要約だけを根拠にしない
- **「作れない根拠は『不明』と書け。それが最も価値のある結果」**
- 引用する `file:行` は実際に開いて確かめた物だけ

返ってきた出典は**この席が抜き取りで開き直す。**1件でも誤引用があれば、その調査全体の精度を疑う。

### 2. 定義を書く

書き方の正本は [reference/definition.md](reference/definition.md)。見本は [examples/sample.json](examples/sample.json)。

**名前は作らない。その repository が既に使っている語をそのまま置く。**`physical` に実装の名前を置き、`name` には「その物を人が呼ぶときの言葉」を置く。日常語で言い切れる語が既に在るならそれを、無いなら folder 名・列名の英語をそのまま使う。読み手のためを思って新しい和名を付けると、**同じ物が2つの名前を持ち、読む側が対応表を暗記させられる。**

**C# で prefix が役割を名乗る repository なら、項目と値は手で書かない。**実体に `code` で型・enum・DDLの表を結びつけ、コードから作る。人が書くのは「どれを載せるか」「名前と説明」「関連の言葉」だけにする。

```bash
python .claude/skills/domain-map/scripts/refresh_from_csharp.py .doc/<名前>/map.json --src src                      # 差分を見る
python .claude/skills/domain-map/scripts/refresh_from_csharp.py .doc/<名前>/map.json --src src --screens            # 画面の増減も見る
python .claude/skills/domain-map/scripts/refresh_from_csharp.py .doc/<名前>/map.json --src src --screens --write    # 書き戻す
```

- 項目の並び・型・enum の値はコードが正。人の書いた名前と説明は物理名で引き当てて残る
- コードにだけある項目は「未命名」で足される。**意味は code の comment・読み書きしている所を開いてから書く** (推測で名付けない)
- 宣言だけで読み書きする所が無い値は「未使用」が付く
- **画面の一覧も code から突き合わせる。**`meta.screenSource` に「画面を登録している所」の探し方を書くと、`--screens` で増減が出る。足すのは題と出典だけで、説明・すること・線画は人が書く。登録 button ではない画面には `manual: true` を付ける (実測 2026-09-18: 2日前に作った地図に、新しい「仕事の地図」画面が入っていなかった)
- ソースは正規表現で読むので Visualizer を起動しなくてよい。`Vo_`・`Inf_` の宣言は、独立に数えたプロパティ数と一致することを確かめてある (実測 2026-09-18: 2,324件中2,324件)

根拠: 実測 2026-09-18。手で書いた auto_work の地図 (09-16) にコードから更新を当てると、2日で増えた項目が15件出た (trigger の `wake_glob`・workflow の `runners`・実行結果の `brainRevision` など)。手書きの項目は書いた日から古くなる。

### 3. 言葉を点検する

```bash
python .claude/skills/domain-map/scripts/check_words.py .doc/<名前>/map.json --src .
```

層と実体の名前を、**その語が repository の code と文書に実際に何 file 出てくるか**で見る。0件なら自分が作った語なので、実物が使っている語へ戻す。`--fields` を付けると項目名も見る (項目名は説明的な句でよいので既定では見ない)。

同じ物の2つの呼び方は機械では分からないので、定義の `meta.words.same` に組で宣言する。使わないと決めた語は `meta.words.avoid` に理由付きで書く。この repository では [.rule/vocabulary.md](../../../.rule/vocabulary.md) が正本で、**brain の語 (persona / profile / trait / trigger / plan) は英語のまま**と決まっている。

**図に出る語には `terms` (用語集) で説明を付ける。**点検はこれも見て、説明の無い表示名を挙げる。日常語に見えて違う物を指す語には `confuse` を書く — その語で読み手が最初につまずく。

根拠: 実測 2026-09-18。PO の「図で使う日本語が微妙。表記ゆれ」という指摘を数えたら、実体名24件のうち **12件が repository のどこにも無い造語**だった (`仕事の札`・`気質`・`流れの設定`・`作業のひと区切り` 等)。同時に `担当` 1語が persona・persona pattern・runner の3つを指していた。`.rule/vocabulary.md` は「同じ物を2つの名前で呼ばない。1つの名前で2つの物を指さない」を正本として持っており、**地図だけがそれを外れていた。**読みやすくしようとして和名を足すと、この形で外れる。

### 4. 配置を探す

```bash
node .claude/skills/domain-map/scripts/layout.mjs .doc/<名前>/map.json --write --er
```

箱の位置 (`at`) を、線の交差・長さ・同じ層 (色) のまとまりで点を付けて探し、定義へ書き込む。業務と画面は筋書きの順があるので既定では動かさない (`--flow` `--screens` で探す)。
開くたびに探すと表示が遅くなるので、配置は定義に書いて図はそれを読むだけにしている。

**`--er` を付けると ER図だけ別に探して `erAt` へ書く。**ER図の箱は項目の数だけ縦に伸びるので、マス目の数ではなく**列の幅と行の高さを実寸で積んだ面積**で点を付ける。画面は横長なので、同じ面積なら横長に置いた方を採る。
根拠: 実測 2026-09-18。手で置いた auto_work の地図は 概念図39・ER図40交差、探索後は 5・19交差。ER図は 2754x2392px あり 1584px の画面から 1206px はみ出していた。実寸で探し直すと 1551x1130px (はみ出し 3px) になった。交差は19→22に増えたが、**画面に入らない図は交差を数える前に読めない。**開くたびに探す版は表示が 0.2秒 → 1.6秒 に延びた。

### 5. 組み立てる

```bash
python .claude/skills/domain-map/scripts/build.py .doc/<名前>/map.json
```

検査に落ちたら HTML は書かれない。誤りの行がそのまま出る (参照先の無い `ref`、同じ位置に2つ置いた `at`、重複した物理名など)。

### 6. 画面で確かめる (省略しない)

**「build が通った」は確かめたことにならない。**図を全部実際に描かせて、目で見る。

- 開き方: browser の pane で `index.html` を開く。file を直接開けない時は、その folder で静的serverを1本立てて `http://127.0.0.1:<port>/` を見る
- 撮って見るなら headless の chrome に `--screenshot` と `--window-size=1600,1000` を渡す (chrome の実行fileの場所は環境で違う)
- 図は URL の `#` で指定できる: `#v=concept` `#v=er&s=entity:<id>&f=<物理名>` `#v=flow&s=step:<id>` `#v=screens&s=screen:<id>` `#v=terms&s=term:<id>`

見る所:

1. どの図でも**線が箱を横切っていないか**、札 (関連の言葉) が読めるか。用語の頁が最後まで並んでいるか
2. 交差が多い・遠回りの線が多いなら 4 の探索をやり直すか、その実体の `at: [列, 行]` を手で直す
   - **まず画面に入っているかを見る。**入らない図は交差の数より先に読めない
3. 左下の凡例が**色の意味**を言えているか (層に `note` を書く)。押すとその色だけ残る
4. 箱に**触れると説明が出る**。`summary` が空の実体・業務・画面は、触れても何も出ない
5. 右の欄が**項目・つながり・出典**まで出ているか
6. ▶ を押して筋書きが最後まで進むか

位置を決める時は、browser の console で `domainMap.layout()` を呼ぶと、今の自動配置が `at` の形で取れる。

線の交差は**数で比べる**。`#measure` を付けて開くと、html 要素の `data-crossings` に図ごとの交差数・多い組・組み立て時間が入る (headless の chrome なら `--dump-dom` で読める。console なら `domainMap.crossings()`)。`at` を動かした前後で同じ数え方で比べ、減った方を採る。
根拠: 実測 2026-09-17。PO が画面UIの格子状の交差を指摘した時、数えると11本で51交差あり、線を束ねて並び順を最適化した後は0になった。見た目の印象だけでは、どの配置が良いか比べられない。

### 7. 報告

1行で書く。何の地図を、どこに、どの時点の実物から作ったか。**不明のまま残した物があれば、その件数も書く。**

## 更新するとき

地図は放っておくと腐る。更新は作り直しではなく**差分の確認**。

1. `.doc/<名前>/map.json` を読む
2. `code` を結びつけた実体は、コードからの更新を差分だけ見てから書き戻す (2 のコマンド)。足された「未命名」の項目に名前と意味を付ける
3. 結びつけていない実体は、`meta.basis` の commit から今までに出典の file が変わっているかを見る (`git log --oneline <前のcommit>..HEAD -- <出典のfile>`)。変わった出典だけ開き直して直す。**変わっていない所の記述を書き直さない** (読み手が「何が変わったか」を追えなくなる)
4. 実体や関連が増減したら 4 の配置を探し直す。名前を足したら 3 の点検を通す
5. `meta.basis` と `meta.generatedAt` を今の値に直し、組み立てて確かめる

## 置き場

- 出来上がりは `.doc/<名前>/`。repository 直下や `projects/` へ散らさない
- 途中の調査結果・script・screenshot は session の scratchpad へ
