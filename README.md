# mem のソース命名と責務分離

## ソースファイルの名前

命名形式の正本は `kiln_studio/_rule/10_writing/source_layout.md#ソースファイルの命名`。
言語にかかわらず、共通実装は `c010read.rs`、kiln固有は `k010_read.cs`、この製品固有は `p010_read.py` の形にする。

- 英字は所属を表す1文字だけ。言語は拡張子で区別する。
- 番号は同じフォルダー・同じ英字の中で管理する。説明や拡張子が違っても重複させない。
- 番号と単語・責務・副作用・実行順を固定の組にしない。説明は実際の責務から選び、複数語を `_` でつなぐ。
- 型・関数・変数の名前は言語の規約を維持する。ファイル名の変更に合わせて型まで機械改名しない。
- import、module、呼び手、設定、試験の発見、生成元を同じ変更単位で揃える。

`p010_validate_input.ts` と `p020_build_query.ts` は書式例であり、番号の予約表や処理順ではない。
同じフォルダーに `p010_read.py` と `p010_write.rs` を置くと、説明と言語が違っても番号の重複になる。

### 固定名を保つ入口

- SvelteKitの `src/app.html` とrouteの `+page.svelte`、`+layout.svelte` はframeworkが発見する名前を保つ。
- Rustの `rag_rust/src/main.rs` はCargoの標準binary入口、`rag_rust/src/m05_api/mod.rs` はRustのmoduleディレクトリー入口。
- `rag_rust/static/index.html` は `main.rs` の `ServeDir::append_index_html_on_directories(true)` がディレクトリーURLの入口として使う。
- manifestやtoolの標準設定名は、実際の読取り元が要求する名前を保つ。

これらの隣にある通常sourceまで例外にしない。第三者コード、生成物、過去のpath・byteを固定した記録は、通常sourceの未移行と区別する。

## 責務と副作用は名前の番号から決めない

featureごとに必要な責務を分ける。下表は設計上の語彙であり、prefixや番号帯の割当てではない。
外部読取りは書込みを伴わなくてもI/Oであり、純粋計算とは区別する。

| 責務 | 担う処理 | 外部との境界 |
|---|---|---|
| 入力検証 | スキーマ・型検証 | ドメインルールの検証とは分ける |
| 入力正規化 | サニタイズ・丸め・トリム | 元入力と正規化後の値を区別する |
| 認証・認可 | 本人確認・操作権限 | 外部照会の有無は実装から判定する |
| 事前条件 | 重複・上限・編集可能状態の確認 | データ取得と条件判定を区別する |
| 入力変換 | HTTP入力からドメイン値への変換 | DB結果の変換とは分ける |
| 読取クエリ構築 | SQLやパラメーターの生成 | この段階でDBへ実行しない |
| 読取実行 | SQL実行、ORMによる取得、キャッシュ参照、結合取得 | 外部読取りI/Oを持つ |
| 結果変換 | DB結果からドメイン値への変換 | 取得と変換を区別する |
| ドメイン処理 | 生成、更新、削除・無効化、計算・集計、ポリシー、状態遷移、ルール検証 | 保存・通知を混在させない |
| 書込クエリ構築 | INSERT・UPDATE・DELETEの生成 | 構築と書込み実行を分ける |
| トランザクション・書込実行 | 保存の整合性と確定 | 外部状態を変更する |
| 出力変換 | レスポンス形式への変換 | 通知やイベント発行とは分ける |
| 外部出力 | イベント、通知、監査ログ、キャッシュ書込み | 外部状態を変更する |

生SQLでは構築と実行を分けると、構築結果とDB接続を別々に検証できる。
ORMでは既存の取得入口で構築と実行をまとめてもよい。分離そのものを目的に同用途の入口を増やさない。

### 経費処理を例にした境界

- 記録: 金額・日付・カテゴリの検証、本人確認、申請上限確認、カテゴリ・為替取得、経費生成、税額計算、申請可否判定、保存、応答、必要な通知を分ける。
- 編集: 変更内容と権限を検証し、承認済みの編集禁止を判定する。既存値への変更差分適用と再計算を、保存処理から分ける。
- 削除: 本人・経理担当の権限、承認・精算状態、対象の存在を確認する。論理削除と物理削除を同じ処理とみなさない。

処理順は呼出し元が持ち、ファイルの番号順から実行しない。

## 構成を選ぶとき

MVCやフラットなfeature構成はファイル数を減らしやすいが、serviceにDB操作・通知・業務判断を混在させない。
クリーンアーキテクチャでは入口・usecase・port・domain・外部実装の依存方向を明示する。関係するfeatureを辿れる配置にする。
DDDでは集約、entity、値object、repository境界、factory、specification、domain eventを必要な規模で選ぶ。
どの構成でも命名形式は同じであり、名前だけで責務分離・副作用の不存在・処理順が保証されたとは扱わない。

## 実装別の入口

- Webの開発・検査・試験・buildは `package.json` の `dev`・`check`・`test`・`build`。
- Rustの起動、API、データの扱いは [RAG Rust](rag_rust/README.md)。seed操作は既存データを削除するため、利用者のDBへ検証目的で実行しない。
- 共通の命名検査は `kiln_studio/tools/50_develop/00_verify/c046verify_source_naming.py --root <memのroot>`。命名の合格とbuild・実操作の成功は別に確認する。
